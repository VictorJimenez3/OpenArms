## Runtime requirements and wiring

- **R1 · Voice.** The parent owns Gemini Live audio and event delivery. Voice can call `Lab.start_task(sid, text, turn_id=completed_turn_id, client_request_id=tool_call_id, record_turn=False)`. Typed input uses `converse`. State exposes `pending` and `tasks`. The gateway should correlate notebook entries by `event_id` and `sequence`, and present exact proposal versions before accepting fresh confirmation.
- **R2 · Expert.** A fully bound, unambiguous active-skill match uses deterministic validated steps. Unfamiliar or changed requests go through expert planning. Cold runs and expert revisions continue to get in-execution tool decisions. Warm runs escalate on unresolved preconditions, failed checks, or unavailable observations. The parent reported qualifying OpenAI Codex gpt-6.1-sol medium via Account 1 with two image/tool calls in 24.98 seconds and a result affected by fresh recorded images. That is a provider-path receipt. This lane ran offline.
- **R3 · Scene.** `Lab._backend` calls optional synchronous `bind_session(sid)` once after construction and before `prepare()`. Inject the parent’s `SceneBackend` factory and producer into the same `Lab`. Async producer methods are `inspect_scene(sid, view)`, `localize_objects(sid, evidence_id, labels)`, and `observe(sid, execution_receipt)`. Inspector and observer supply `scene.fresh` and validated image references. Optional `scene.expires_at` uses host Unix seconds. Checkpoints require a new image evidence ID. Observed results require independent provenance, observer version, and fresh image evidence. The producer and adapter own PNG path and byte validation.
- **R4 · Execution feedback and consent.** `expert.run` receives evidence, tools, the approved plan and execution feedback. It can propose a freshly consented revision before motion or change the observation after motion. Once a mock action was dispatched, subsequent task revisions are observation-only. STOP and reconnect revoke stale work; restart never replays approved tasks. Controller and independent observation events remain separately correlated. The parent owns transport playback and completed-utterance consent.
- **R5 · Skills.** `PlanDraft` accepts the typed operations in `PRIMITIVE_SCHEMAS`. For example, an action sequence in three separately consented requests can use `mock_pick_up(fixture=sample_cup, station=A)`, `mock_pour(fixture=sample_cup, station=C, portions=1)`, and `mock_put_down(fixture=sample_cup, station=B)`. Each plan allows one action plus an earlier image checkpoint and final independent outcome checks. The backend starts with one cup at A, allows pickup and placement at A/B, and allows one full-cup pour into C. It publishes `holding`, `cup_station`, `cup_portions`, and `receiver_portions` as mock state. The backend override should keep the world consistent with successful execution; cancelled or failed operations can reach a progress callback before applying controller state. It should accept keyword-only `operation='mock_prepared_sample'`, forward it to `super().execute_step`, and update the synthetic world for the matching named operation phase. The prepared sample retains its original three phase names and caller signature. Record the shared example in `docs/INTERFACES.md` at integration. The split between bounded actions and local execution follows the [action catalog research](../research/duc/harness.md#part-b-tool-layers-and-the-action-catalog).
- **R6 · Evaluation.** `start_improvement` pins an earlier failed check or unknown observation and its feedback. `evaluate_candidate` requires a completed candidate task with independent observer feedback and records the injected evaluator’s exact candidate/baseline decision. Keep the prior active version on rejection. The real runner still needs to provide frozen-suite artifacts and promotion measurements.
