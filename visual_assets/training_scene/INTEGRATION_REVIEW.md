## Runtime work required before these assets become runnable experiments

1. Runtime owner implements `IsaacBackend` (proposed name), `mode='simulated'`, against `ExecutionBackend`, injects it via `backend_factory`, reports only verified capabilities and preserves request identity, STOP, timeout and single-use execution behavior. Multiple sessions sharing one simulator need an explicit simulation ownership lock: the current motion lock applies to physical mode. Scene state/reset must not leak between sessions.
2. Integrator adds versioned experiment-specific request parameters, validators, catalog entries and skill scopes. Preserve strict validation and separate physical capability from simulated qualification. One minimal integration can initially route supported A/C→B sample transfers to the density scene using episode-side condition metadata; that does not unlock sorting bins, precise rack insertion, lever pockets or dipping. Density still requires actual release and outcome evidence.
3. Runtime owner supplies the original SO101 articulation, controller/joint mapping, collision geometry, mass/inertia, contact materials, gripper/release detection, reset(seed, condition), settle/termination rules, physics step and camera/render configuration. Asset owner supplies named fixture geometry, target frames, camera transforms and stable semantic IDs. Agree coordinate axes, meters versus millimeters, up axis and joint units explicitly at import. Materials and rendered water are not physics implementations.
4. Add per-task outcome evaluators from measured simulator state and a separate observation/perception path from the fixed cameras. Ground truth is evaluator-only unless a benchmark explicitly declares state input. Completion, grasp, release, target occupancy and science response are separate facts. Fault, no contact, occlusion, dropped video or missing state produces failed/unknown status, never a manufactured pass.
5. Add density and pH analytical model modules with explicit versions/parameters and `MODEL-PREDICTED` provenance. A rendered model response remains model-generated even when photographed by a simulated camera. For ramp/lever use dynamic state from PhysX, with no scripted trajectories or auto-level drive after release. Inspect the installed Isaac/PhysX version: linked PhysX documentation demonstrates engine mechanisms, not local installation or validated scene behavior.
6. Export an episode bundle plus new versioned `experiment.json`, `metrics.json`, evaluator-only `oracle.jsonl` and model-output sidecar as needed. Reuse the existing camera/trace validator without claiming a new generic skill compiler exists. Extending bench skill compilation and simulated skill promotion requires integrator-owned changes and a distinct evidence policy. Learning/quiz definitions also need to accept the new experiment IDs rather than fall through to unrelated transfer guidance.

Concrete proposed handoff: `reset(episode_id, experiment_id, condition_id, seed)` is harness metadata, followed by a separately validated robot skill request. Adapter returns request-bound `ExecutionResult(backend='simulated', physical_success=null, observation=Observation(provenance='SIMULATED', source='isaac_state_evaluator:<version>', value={robot_task_status, measurements, episode_id}, evidence=[relative_receipt_path]))`. Analytical science gets a separate `MODEL-PREDICTED` record, not a mislabeled field in that observation. These are proposed behaviors, not new callable APIs supplied by this review.

## Candidate assessment

| Candidate | Scientific interpretation | Main qualification risk |
| --- | --- | --- |
| Vial placement repeatability | Robotics metrology: compare within-condition dispersion and target error | A hole needs real concave/compound collision geometry; target reset and fixture dimensions must be measured. A render of an inserted vial proves nothing about execution. |
| Sample sorting | Perception plus correct destination manipulation; no chemical identification | Two destinations and size inference are outside current grammar. Randomize bin side so a fixed route cannot pass by shortcut. |
| Density | Ideal buoyancy model paired with robot release; matches current lesson constants | This tests model integration and manipulation, not independently discovered fluid behavior. No native liquid simulation is assumed. |
| Ramp friction | PhysX contact simulation compared to Coulomb reference | Friction values must be effective pair values; combine mode, release impulse, collision shape and solver settings can dominate the result. |
| Lever balance | PhysX hinge dynamics compared to signed gravity torque | Loading lock must be removed after gripper clears. Zero torque is neutral, not a restoring spring; start level and disable drive. |
| pH indicator | Indicator model and camera readback after validated immersion | No real chemistry is solved. Do not infer pH from an arbitrary color material or claim equilibrium/kinetics validation. |

If choosing three for breadth, qualify vial placement, density and ramp friction first: baseline manipulation, reuse of an existing educational model, and a genuinely dynamic contact task. Sorting is a useful alternative when perception is the training priority. Lever adds joint configuration and locking; pH adds a new motion primitive and synthetic chemistry. This prioritization is a design recommendation, not a user selection or claim of runtime readiness.

## Development/evaluation protocol that avoids answer leakage

- Freeze the task definition, success tolerance, observation modality and failure policy first. Record original SO101 asset hash, scene/collider/material hashes, camera intrinsics/extrinsics, fixture IDs, model version, simulator build, physics step, solver settings, controller/skill/policy version and random seeds. Keep front and overhead cameras fixed throughout each declared setup; any mount change creates a new setup/calibration identity.
- Suggested pilot: 20 development episodes per condition per selected task, then 30 fresh held-out evaluation episodes per condition. These are planning counts, not completed trials or adequate evidence of real-world reliability. Split by base scene/reset family, source placement and sample instance, not by frames from the same trajectory. Never place near-duplicate renders, replayed trajectories or revisions of the same reset across train/evaluation. Distinguish training episodes from development validation used to choose a policy.
- Development can expose full diagnostics and permit expert skill revisions. Freeze the resulting skill/controller/model hashes before evaluation. Evaluation resets/seeds and outcome labels are withheld from policy prompts, tools and reusable-skill compilation. Condition values legitimately supplied as student instructions remain allowed inputs; expected outcomes and evaluator state do not. In a camera-only task, filenames, IDs, HUD labels, color-by-class fixtures, oracle channels and JSON sidecars must not reveal the answer. Supply scene/task metadata through separate policy and evaluator views, not a shared readable directory.
- Match expert, cached-skill and revised-controller runs on the same held-out reset IDs and instruction set; randomize run order and reset completely. Evaluate source offsets, sample identities, bin sides and light variations within declared feasible bounds. Equal observation/action budgets matter. Seeds enable pairing, not a claim that identical deterministic repeats are independent evidence.
- Do not improve policy/skills after seeing held-out failures and then reuse the same set as final evaluation. Once inspected for repair, retire that set to development and generate a new held-out set. Predeclare supported distributions; evaluate harder unseen ranges separately as out-of-distribution results.
- Log every attempted episode, including startup failures, invalid resets, STOP, grasp failure, misses, unknown evidence and camera loss. Predeclare exclusions; report attempted/valid/excluded/failed/unknown counts separately. Primary success is observed task success divided by attempted valid task episodes; also show end-to-end success including infrastructure failures. Attach raw front/overhead clips, action/joint traces, evaluator receipts and model provenance.
- Report counts and uncertainty (for example Wilson intervals on proportions), condition-wise success and paired improvement. A state evaluator and analytical reference sharing the same implementation only test consistency. Validate independent equations/fixtures separately, and never infer physical SO101 or wet-lab performance from simulated results.

Only publish measured metrics with explicit denominator, time window and provenance. Use null plus reason for unavailable values; never substitute zero. A fast call-count reduction is not robot learning unless the measured controller/policy behavior improves under a frozen comparison.

## Source verification and limitations

The candidate constants are design choices. Science equations and supported engine mechanisms were checked against these first-party teaching/engine sources; this review adds no broad research claims:

- [OpenStax: Archimedes' principle](https://openstax.org/books/university-physics-volume-1/pages/14-4-archimedes-principle-and-buoyancy): buoyancy and floating density relation.
- [OpenStax: friction](https://openstax.org/books/university-physics-volume-1/pages/6-2-friction): static/kinetic Coulomb reference.
- [OpenStax: static equilibrium](https://openstax.org/books/university-physics-volume-1/pages/12-1-conditions-for-static-equilibrium): force and torque balance.
- [OpenStax: acid-base indicators](https://openstax.org/books/chemistry-2e/pages/14-7-acid-base-titrations): acid/base indicator equilibrium and bromothymol-blue transition interval. The model's pKa=7.1, color interpolation and dip timing are explicitly illustrative design parameters, not calibration evidence.
- [NVIDIA PhysX 5.4.1: rigid-body dynamics](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/docs/RigidBodyDynamics.html): mass/inertia, contacts and material-friction configuration.
- [NVIDIA PhysX 5.4.1: joints](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/docs/Joints.html): revolute joint mechanism, drives/limits and radians convention.

Inspection was source-only. No Isaac launch, GPU access, controller execution, bench test, camera calibration or model training was performed. JSON validity, six distinct IDs, two numerical conditions per candidate and the required capability label were checked locally. This review does not claim the surrounding runtime worker has or has not implemented additional support elsewhere; it describes the inspected agentic/bench seams at the recorded snapshot.
