## Decisions to carry between chats

Keep the result understandable without relying on color or video alone. - **Constrained adaptation.** “New environment” first means familiar capabilities in a versioned lab setup with different objects, station bindings, or observations. The expert can use tools to resolve those differences and compose a candidate for that setup. If an experiment also needs a new action or observable, someone must supply and qualify that capability. Treat arbitrary benches, automatic physical transfer and generic robot control as claims requiring separate evidence. [Delivery contract](../../docs/FULL_SYSTEM_DELIVERY.md)

## Student and agent flow

| Stage | What the student does or hears | What the system does |
| --- | --- | --- |
| Start | Select or enter the prepared activity and ask what is ready. Choose an action by voice or text. | Provide the current setup, available actions and evidence source. Keep transcript, status and direct STOP available while the expert works. |
| Understand | Hear an acknowledgment. Answer a short clarification if the target or amount is unclear. Ask a question while planning runs. | The conversational agent responds immediately and sends an actionable turn to the background task loop. The expert checks current scene evidence and allowed capabilities. Use a matching validated skill if its bindings and preconditions hold. |
| Review | Hear or read the proposed action with the target and any amount that matters. Confirm it or correct it. | The server validates and binds an exact proposal to current evidence and state. Fresh consent applies to that presented version. Corrections require a new proposal, and real motion retains separate operator authorization. |
| Act and observe | Hear progress, stop if needed, and get a plain description of what was observed, with units where applicable. | A bounded executor dispatches once and reports status. An independent observer reports a separate outcome. Send both receipts to the task loop and the conversational agent. Fresh checkpoint evidence can inform the expert's next bounded decision. |
| Decide what’s next | Ask what the result means, repeat, or change a condition. If the result is unreadable, decide whether to try again. | State the provenance and any uncertainty. Keep history, including failures. Cancel/STOP or a dropped connection revokes stale approval. Reconnecting restores history and requires a fresh request or confirmation as applicable. |

**Example to test:** In the retained indicator fixture, ask to check the prepared vinegar sample, then correct it to water before confirming. Ask what the agent is doing while it works. Hear the exact replacement proposal, confirm it once, and get the observed simulated color or `UNKNOWN`. Then ask to compare or repeat. Exercise STOP as a separate run. The indicator is a known regression fixture and can be used while the real kit activity is undecided. ## How the system gets easier to use

1. **Known setup and supported request.** Match an active skill, bind the student's parameters, check fresh scene state, and use deterministic actions and observation checks. Keep progress, correction, confirmation and STOP available on the fast path.
2. **Unfamiliar request or changed setup.** Give the expert the task, timestamped scene, available tools and environment limits. Clarify missing inputs, inspect the scene, and compose a typed candidate from supported actions. If a binding, camera check, or capability is missing, report it and ask for the smallest useful correction. Reuse a skill definition across setups only after the destination setup's bindings and checks validate. Keep older approvals and admission receipts scoped to the environment they cover.
3. **Prepare and improve before students need it.** When the bench or scene is set up, use representative requests and recorded outcomes to author and validate skills. For a recorded limitation, keep the original skill fixed, test a substantive candidate on the same cases including a held-out variation, and promote only through the existing evaluator and registry. An active skill should remove avoidable reasoning or repeat work and keep observation and consent checks. Run development attempts before the student session where possible.

NVIDIA’s Astranomy evaluated general-purpose pick-and-place on RoboLab-120. Its Direct Policy averaged 18.56 seconds per inference call. That gives a reason to measure our own student-facing delays and use local execution for repeatable lab actions. ASPIRE demonstrates learning reusable behavior from traced failures. The OpenArms adaptation is to propose and evaluate bounded skill definitions for a prepared lab, with separately qualified motion and tools. The papers supply design evidence. OpenArms needs its own measurements for latency, reuse and transfer. [Astranomy](https://research.nvidia.com/labs/srl/projects/astranomy/) · [ASPIRE](https://research.nvidia.com/labs/gear/aspire/)
