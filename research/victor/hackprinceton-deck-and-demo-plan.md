# OpenArms judging deck and live demo

Working storyboard · November 15, 2026 · Three slides plus a technical appendix

Target **1:50** including the live action, with **10 seconds in reserve**. The 45-second live segment is a timing budget to verify with the final setup. Open with the student's decision, get the arm moving in the first minute, and give the learning-and-reuse result a full slide. Keep the physical activity to the one prepared two-vessel station. Offline simulation clips and a preloaded trace keep the sequence repeatable for successive judges.

### Exhibit and appendix

- **Architecture slide for questions.** Voice or text → current scene and exact proposal → bounded executor → independent observation → spoken/text result. Add an unfamiliar-task branch to the expert and a matching-skill branch to the registry. Show that scene checks and authorization apply on both branches. In the evidence panel crop to the actual action, observation and saved skill. Keep credentials and session IDs out of the export.
- **Changed-layout slide for questions.** Capture a controlled change in the simulated positions of the dock or receiver. Show the baseline setup, the new camera evidence and a recorded supported adjustment, clarification or refusal. The Smartivity branch has a paired fixed-versus-camera-registered Volcano diagnostic. Label that comparison as local motion logic with zero policy calls. Show a fresh expert trace separately if using it as evidence of LLM adaptation. If a fresh trace is unavailable, keep the exact alternative in Q&A: the recorded demo-bench expert declined C→A, and the Volcano regression checks one fixed-target miss against successful camera registration on the same seeded layout. [Typed benchmark](https://github.com/VictorJimenez3/OpenArms/blob/fcce2324f4c8fafcef84cd2e24ccecf9464af32e/research/duc/demo-bench-integration.md) · [Registration regression](https://github.com/VictorJimenez3/OpenArms/blob/8eb84faf305f64d142a94ccc12db13fcc69baa1b/simulation/tests/test_smartivity_world.py#L123-L132) · [Registration diagnostic source](https://github.com/VictorJimenez3/OpenArms/blob/8eb84faf305f64d142a94ccc12db13fcc69baa1b/simulation/openarms_sim/smartivity_trials.py)
- **Evidence and next pilot slide.** Show the physical run that actually passed on the final station, what was separately verified in simulation and what remains open. For next steps name one teaching-lab activity and have students and TAs check command clarity, ease of correcting/stopping, comprehension of the result and reset workload. The student remains the experimenter.
- **Visual treatment.** Use 16:9 slides, a still from the real bench on slide 1, matching crops of the simulator on slide 3, and readable labels on screenshots. Use large high-contrast text, captions for important audio, and words alongside color changes. Show the two relevant states on a single slide so the audience can follow from across the table.

## Rehearsal and fallback

1. **Qualify the physical cue.** The selected route is donor A → receiver C → donor A → HOME. Start with the prepared magic-tea indicator and citric-acid solution only if the team gets a readable, repeatable physical result. Contained fizz is the alternate candidate. Qualify the exact materials, geometry, operator authorization, STOP, actual observation, reset and timing with the bench team. The repo records a separate supervised mandarin transfer. The bench panel's pour path remains simulation-only in the reviewed main snapshot. Select the actual qualified execution path during rehearsal. [Wet-lab procedure](https://github.com/VictorJimenez3/OpenArms/blob/fcce2324f4c8fafcef84cd2e24ccecf9464af32e/docs/WET_LAB.md) · [Current bench lane](https://github.com/VictorJimenez3/OpenArms/blob/fcce2324f4c8fafcef84cd2e24ccecf9464af32e/docs/LAB_RUNBOOK.md#real-bench-lane-optional-camera-simulated-preview-then-the-real-arm) · [Physical rehearsal issue](https://github.com/VictorJimenez3/OpenArms/issues/12)
2. **Verify the exact student interface in the room.** Test one judging device with audible speech, transcript or text fallback, consent and STOP. Make the transcript readable from the table. Rehearse a correction separately. If the app cannot drive the bench by voice, show the actual supervised execution and identify who triggered it. If using the typed simulation as the voice backup, keep it labeled. Use “I couldn't verify the result” when observation is unclear.
3. **Capture genuine proof before the round.** Keep a continuous view of request, consent, arm movement and outcome for the physical fallback when that chain is available. For a bench-operator fallback, show the actual trigger. Save a small receipt with the commit, client, backend, selected recipe, cold/warm version and counts if applicable, elapsed time, observations, failures and interventions. Preload the clip, simulation montage and slide PDF. Rehearse the switch without internet.
4. **Use the fallback early.** If the connection, arm readiness or observation fails, the bench operator uses the rehearsed stop/recovery procedure. Move to the qualifying recording and say “This is a recording from rehearsal.” If no wet-lab rehearsal passed, a qualified water motion check or earlier dry transfer can show hardware separately, with its own label. Show the modeled reaction as simulation. The audience should know whether a run used voice, text, an operator or a recording.
5. **Run two timed handoffs.** Suggested roles: Victor leads the story and the AI trace, Joseph checks the student UI and audible interaction, Duc owns supervision/reset with the bench team, and Stefanie cues verified media. Confirm roles together. Time the entire request, confirmation, pour, return and observation on the actual station. Log whether the live segment fits in 45 seconds and total delivery fits in 2:00. If the complete sequence overruns, use the rehearsed recording to show the result and describe only the physical action the audience saw live. Let the operator handle recovery while the speaker moves on to slide 3.
